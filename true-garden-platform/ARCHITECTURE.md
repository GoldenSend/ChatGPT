# Track C: the smallest credible PS4-specific Linux platform (design only)

Status: **DESIGN ONLY.** Nothing here is built or approved. No migration of the live install. Each layer says what exists today (`WORKING`), what is proposed (`PROPOSED`), and what would have to be proven first.

## Principle

Debian stays the base. The "PS4 platform" is a **thin, versioned support layer** on top of an ordinary Debian root: one kernel patch set, one firmware/boot bundle, one graphics runtime, and a handful of health tools. It is not a new distribution. Every artifact is pinned by hash and built reproducibly, and every boot set has a rollback twin.

## Boot-set procedure (how any kernel/initramfs change would happen)

1. Build offline, record hashes in a new `BOOTSET.json`.
2. Go/no-go gate: owner present, current boot ID, rollback files on the FAT with hashes, no GPU or SATA test in the same window.
3. Owner-approved write of the new files beside the rollback.
4. One boot, read-only verification, results recorded.
5. On any failure: restore the rollback set from the IdeaPad (or SanDisk boot), no retry until reviewed.

## What this deliberately excludes

- No native cold boot. It isn't possible without Orbis, and claiming it would be false.
- No internal-HDD root, no Orbis partition access.
- No system-wide Mesa or kernel upgrade without the boot-set procedure.
- No new controller or authority: GoldenPi remains the only Atom authority. The PS4 stays a worker.
- Atom Medic and other fleet agents stay out of scope.

## Order of work (if Track C is later approved)

1. Read-only probe (R1) and the carrier-guard proof (R2).
2. `BOOTSET.json` + send wrapper (no PS4 change).
3. Boot-diagnostics initramfs hook (one boot).
4. Kernel queue step (a): SCLK measurement → patch; read-only fan; satadiag1 with persistent read-only.
5. Health timer.
6. Only then consider a 6.x Belize base.
